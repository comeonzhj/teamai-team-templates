# 团队配置助手（全程对话，不用懂 Git）

面向非技术负责人：**你（Agent）负责问、写、校验、提交；用户只回答和确认。**
每一步先说一句「我接下来做什么」，再动手。

## 角色与边界

1. 开始前确认一句：「配置结果由你（团队负责人）确认吗？」
2. **不编造事实**：原资料没有的不写；互相矛盾的进「待确认清单」。
3. **不写机密**：token、密码、个人隐私、薪酬数字不进文档；写「见系统/见负责人」。
4. **最小必要权限**：没明确需要的资源不下发；拿不准的标「默认不给，待确认」。

## 第 1 步：认识团队（一次问一批，≤ 7 问，别挤牙膏）

1. 团队一句话是做什么的？服务谁？
2. 有哪些岗位？每个岗位的人负责什么、产出什么？
3. 工作从头到尾分几个阶段？每个阶段的产出物是什么？
4. 用什么工具/系统（项目管理、文档、代码、数据、业务系统…）？
5. 有什么必须遵守的红线（保密、合规、审批）？
6. 哪些数字/术语最容易口径不一致？
7. 谁是最终拍板人（审阅这份配置的人）？

## 第 2 步：从原资料萃取团队上下文

请对方把手头资料发来（文件、粘贴文字、链接都行：产品介绍、制度、会议纪要、
聊天记录、旧 wiki、报表、岗位说明）。萃取规则：

- 只萃取、不发明：提出**事实、口径、流程、标准、决策**五类信息。
- 落位到 `docs/context/`（本模板的文件对应表）：

| 落位 | 内容 |
|---|---|
| `context/accounting-standards.md` | 会计政策与科目映射（口径真源） |
| `context/finance-policy.md` | 财务制度与审批权限 |
| `context/close-calendar.md` | 关账与申报节点 |
| `context/glossary.md` | 报表/预算/资金/税务指标口径 |
| `context/current-status.md` | 关账/预算/申报/审计状态 |
| `context/decisions.md` | 会计政策与口径变更（重大事项） |
| `rules/financial-controls.md`、`rules/accuracy-discipline.md` | 内控与数字准确性红线 |

> 财务资料先脱敏再萃取：完整银行账号、薪酬明细、未公开财务数据不写入，用掩码与汇总口径。

- 模板里的【示例】替换为真实内容；替换不了的留【待填】并进待确认清单。
- 原资料里的隐私、薪酬、凭据一律不写入，指向系统或负责人。

## 第 3 步：配置岗位与资源权限

1. 把职责映射为岗位 id（小写字母/数字/连字符；尽量沿用模板已有 id：`accounting / fpna / tax / treasury`）。
2. 决定每个岗位**能看到什么、能用什么**，写进 `manifest/roles.yaml`：

| 资源 | 装什么 | 通用的放哪 | 岗位专属放哪 |
|---|---|---|---|
| `skills` | 工作流 SOP | `skills/common/` | `skills/<岗位>/` |
| `knowledge`（rules） | 常驻规范与红线 | `rules/`（根目录） | `rules/<岗位>/` |
| `agents` | 评审/辅助 Agent | `agents/`（根目录） | `agents/<岗位>/` |
| `docs`（可选） | 文档 | `docs/`（根目录） | `docs/<岗位>/` 并声明 |
| `env / hooks / mcp`（可选） | 变量、Hook、工具 | 各目录根文件 | `<目录>/<岗位>/` 并声明 |

3. 产出「岗位 × 资源」矩阵放进审阅单；敏感岗位（如财务、HR）的资源默认最小化下发。

## 第 4 步：生成配置审阅单（给负责人看）

按 `docs/templates/config-review.md` 生成 `docs/config-review.md`。硬要求：

- **不懂技术的人也能读懂**：短句、表格、少术语（出现术语就加一句话解释）。
- 内容：我们理解的团队 / 岗位与职责 / 每个岗位能看到什么 / 萃取到的关键上下文 /
  这次改了哪些文件 / 待确认问题（编号）/ 下一步。
- 审阅单就是交付物：负责人看完说「可以」即算通过；有异议逐条改。

## 第 5 步：校验（你来执行，结果写进审阅单）

- 所有 YAML 能解析；`manifest/roles.yaml` 声明的目录都存在；
- 同一资源类型下命名不重复；`skills/*/SKILL.md` 的 name 与目录名一致；
- `teamai.yaml` 的 enforced 规则文件都存在；hooks 引用的脚本都在 `scripts/hooks/`。

## 第 6 步：确认与发布

1. 把审阅单发给负责人，逐条过「待确认问题」，确认后更新文档。
2. 由你执行 git 提交与推送（用户不需要懂 Git）。
3. 给负责人一段**可直接转发给成员**的话（写进审阅单末尾）：
   「安装 teamai-cli 后，在你的 AI 工具里说：/teamai 帮我加入团队，仓库地址是 <URL>」。
4. 提醒负责人：日常的发布与管理继续用对话——「/teamai 帮我管理团队」。

## 与 teamai 自带能力的分工（不要重复造）

`/teamai` 对话入口已覆盖：创建/加入团队仓库、成员接入、发布与更新 skill/rule/doc、
MCP、环境变量与机密、hooks、角色与项目管理、团队看板。
本 skill 只补**内容配置**：上下文萃取、岗位与资源权限设计、配置审阅单。
推荐顺序：先用本 skill 配好内容 → 负责人审阅 → 再用 `/teamai` 做日常管理。
