# 阶段 3 · 交互与视觉设计（Design）

> 主责：Design ｜ 协作：PM（目标与文案）、Dev（实现成本与技术约束）
> 产出物流向：→ 阶段 4 开发

## 目标

交付**研发可直接实现、测试可直接转用例**的设计包，并保证体验一致性与可用性。

## 进入条件

- 需求卡片 / PRD 评审通过，AC 与非目标明确（阶段 2 DoD）。

## 关键动作

1. **设计简报**（`../templates/design-brief.md`）：目标、场景、约束、成功指标；与 PM 确认。
2. **方案探索**：≥ 2 个方向 + 取舍对比；低保真定结构 → 高保真定细节。
3. **设计系统复用**：组件取自 `DESIGN_SYSTEM_URL`；偏离需说明并回馈维护清单。
4. **状态设计**：空 / 加载 / 错误 / 无权限 / 极端长度。
5. **可用性走查**：Nielsen 启发式 + 无障碍基本项（对比度 4.5:1、焦点态、44px 触达、替代文本）。
6. **设计评审**：PM（目标达成）+ Dev（实现成本）+ QA（可测性）三方过稿。

## 产出物

- 设计交付包：标注稿、状态覆盖表、交互/动效说明（时长、缓动、触发）、文案终稿、切图规范、走查结论

## DoD（完成定义）

- [ ] 五类状态全部有设计
- [ ] 文案终稿（按钮/空态/错误提示）
- [ ] 多端/断点差异逐条说明
- [ ] 走查结论附上，遗留问题有 owner
- [ ] Dev 评审过实现成本，结论写入 `../context/decisions.md`（如有取舍）

## 交接

→ Dev：设计交付包 + 约束清单 + 已否决方向（见 `stage-handoff`：设计→研发交接包）
→ QA：设计包中的状态矩阵可直接转测试用例

## 常见坑

- 只设计正常流，异常态留给研发即兴。
- 交付「同移动端」一句话断点说明。
- 研发实现与稿子不一致时互相迁就，最终体验走样（规矩：改实现或改稿，二选一并留痕）。
