# 阶段 5 · 测试与质量（Testing）

> 主责：QA ｜ 协作：Dev（修复、定位）、PM（缺陷取舍）
> 产出物流向：→ 阶段 6 发布

## 目标

用数据回答「能不能发」：验证 AC、暴露风险、给出发布建议。

## 进入条件（测试准入）

- 提测包齐全（技术方案、变更清单、影响面、自测报告）；
- 冒烟通过、环境可用、测试数据就绪。不满足 → 退回，不硬测。

## 关键动作

1. **测试方案**（`../templates/test-plan.md`）：范围、策略（自动化/手测/探索性）、风险矩阵、准入准出、环境数据。
2. **用例设计**：等价类 + 边界值 + 错误猜测 + 场景法；核心链路正向/反向/边界三类。
3. **执行**：按优先级 P0→P3；每日测试结论写数据（执行数、通过率、新增/遗留缺陷、风险）。
4. **缺陷管理**：分级（P0 阻塞发布 / P1 严重 / P2 一般 / P3 轻微）；必须可复现；P0/P1 24 小时内给定位结论。
5. **回归**：按「改动影响面 + 历史缺陷热点」选范围并写明理由。
6. **准出评估**：给发布建议（可发 / 带风险发 / 不可发），列遗留风险与处置。

## 产出物

- 测试方案、用例集、缺陷清单、测试报告（数据化）、发布建议

## DoD（完成定义）

- [ ] AC 100% 覆盖，结果可追溯到用例
- [ ] P0/P1 清零；P2 有处置结论（修/延期需 PM 签字）
- [ ] 核心链路回归通过，性能基线达标
- [ ] 测试报告含数据与遗留风险
- [ ] `current-status.md` 更新为「待发布 / 可发布」

## 交接

→ 发布：测试报告 + 遗留缺陷处置 + 发布建议 + 回归范围与结果（见 `stage-handoff`：测试→发布交接包）

## 常见坑

- 「测试通过」四个字交差，没有数据。
- 回归只测改动点，忽略受影响的老功能。
- P2 缺陷无结论地挂着，上线后变成线上问题。
