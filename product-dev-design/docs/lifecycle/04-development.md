# 阶段 4 · 技术方案与开发（Development）

> 主责：Dev ｜ 协作：QA（测试左移）、Design（还原度）、PM（AC 澄清）
> 产出物流向：→ 阶段 5 测试

## 目标

按 AC 实现功能，交付**可评审、可测试、可回滚**的代码。

## 进入条件

- 需求 AC 明确；设计交付包齐全（UI 需求）；或技术预研结论已给出。
- **带风险进入**（如设计未定稿）必须在 `current-status.md` 标注风险与兜底方案。

## 关键动作

1. **技术方案**（> 3 人日必写，`../templates/tech-design.md`）：方案对比、数据模型/接口变更、兼容迁移、回滚策略、灰度/开关、可观测性、性能预算、风险。
2. **任务拆分**：按可独立交付/可独立测试的粒度拆，每项有 owner 与预估。
3. **编码**：小步提交（Conventional Commits）、测试先行、禁止项见 `rules/dev/dev-standards.md`。
4. **自测**：AC 逐条自测 + 影响面回归；产出自测报告。
5. **代码评审**：CR ≤ 400 行，看正确性/可读性/测试/AC 覆盖；4 小时内响应意见。
6. **提测准备**：变更清单、开关状态、部署说明、已知风险。

## 产出物

- 技术方案（评审通过版）、代码（合入主干）、自测报告、提测说明

## DoD（完成定义）

- [ ] AC 逐条自测通过并留有记录
- [ ] 新逻辑有测试；修 bug 有复现测试
- [ ] CR 通过，无阻塞意见
- [ ] 回滚方案与开关状态写明
- [ ] `current-status.md` 更新为「待提测」

## 交接

→ QA：提测包 = 交接包（00-summary + 技术方案 + 变更清单 + 影响面 + 自测报告 + 已知风险）
→ Design：还原度走查（差异要么改实现要么改稿留痕）

## 常见坑

- 方案不写回滚，发布当天才发现退不回去。
- 提交里夹带无关改动，CR 变成考古。
- 带风险进入却没人跟踪风险（状态文档必须记录）。
