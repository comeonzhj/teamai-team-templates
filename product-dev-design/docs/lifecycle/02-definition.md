# 阶段 2 · 需求定义与评审（Definition / PRD）

> 主责：PM ｜ 评审方：Design + Dev + QA（三方缺一不算通过）
> 产出物流向：→ 阶段 3 设计（并行可启动阶段 4 的技术预研）

## 目标

把需求候选变成**范围清晰、验收可测、三方共识**的可开发需求。

## 进入条件

- 阶段 1 DoD 达成；价值假设与成功指标明确。

## 关键动作

1. **写 PRD / 需求卡片**（`../templates/prd.md` / `requirement-card.md`）：背景、目标与非目标、用户故事、功能说明、AC、数据口径、埋点需求、异常与边界、灰度与回滚要求。
2. **AC 逐条可测**：Given/When/Then；覆盖正常流、异常流、边界、权限、性能。
3. **预沟通**：与 Design 走查体验路径，与 Dev 做可行性与复杂度预判（> 3 人日的提示补技术方案）。
4. **需求评审会**：逐条过范围与 AC，记录分歧与结论；目标是共识，不是宣讲。
5. **评审后 24h 内收尾**：更新 PRD、排期假设、`current-status.md`、`decisions.md`。

## 产出物

- PRD / 需求卡片（终版，AC 完整）
- 排期估算（RICE + Effort）与依赖清单

## DoD（完成定义）

- [ ] 目标、非目标、范围三者写清
- [ ] 每条 AC 可验证，QA 可直接转用例
- [ ] 产品 + 设计 + 研发三方签署（缺席方书面确认）
- [ ] 数据口径与埋点需求明确
- [ ] 灰度与回滚要求已写明

## 交接

→ Design：需求卡片 + AC + 约束 + 已否决方向（见 `stage-handoff`：需求→设计交接包）
→ Dev：> 3 人日的需求同步启动技术方案（阶段 4 可并行）

## 常见坑

- AC 写成「体验流畅」「性能达标」——不可测，等于没写。
- 非目标缺席导致范围在开发期膨胀。
- 评审会只讲不决，结论留在群里。
