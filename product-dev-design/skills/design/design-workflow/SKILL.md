# 设计工作流（Design）

## 1. 设计简报（先于一切稿子）

按 `docs/templates/design-brief.md` 填：目标与成功指标、用户场景、约束（平台规范 / 设计系统 / 性能 / 合规）、参考与反例、时间与交付形态。简报与 PM 对齐后再出方案。

## 2. 方案探索

- 至少 2 个方向（信息架构或交互路径层面的差异，不是换颜色），各写一句「适合谁 / 牺牲什么」。
- 用低保真验证结构，用高保真定细节；不要在低保真阶段抠像素。
- 关键流程做「任务流走查」：用户从入口到目标需要几步、每步的认知负担是什么。

## 3. 设计系统与一致性

- 组件、间距、字号、色板一律取自设计系统（`DESIGN_SYSTEM_URL`）；确需新增组件，先查重再提需求，并同步维护清单。
- 多方案对比时给决策表（维度 × 方案），结论写入 `docs/context/decisions.md`。

## 4. 可用性走查（交付前自检）

- Nielsen 启发式逐条过：系统状态可见、贴合现实、用户控制与自由、一致性、防错、识别优于回忆、灵活高效、克制设计、容错、帮助文档。
- 无障碍基本项：对比度 ≥ 4.5:1、可聚焦元素有可见焦点、触达区域 ≥ 44px、图标配文字替代。
- 空 / 加载 / 错误 / 无权限 / 极端长度五类状态必须有设计。

## 5. 交付包（见 `stage-handoff` skill）

标注稿 + 状态覆盖表 + 交互与动效说明（时长、缓动、触发）+ 文案终稿 + 切图/导出规范 + 走查结论。研发实现与稿子不一致时二选一：改实现或改稿留痕，不允许「差不多」。

## 6. 设计变更管理

变更用「变更说明」（改了什么、为什么、影响哪些页面/接口/排期）发出，并更新 `current-status.md`；被否决的方向也记录，避免反复重提。
