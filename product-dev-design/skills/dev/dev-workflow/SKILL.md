# 研发工作流（Dev）

## 1. 接活先对齐

- 读 `docs/context/current-status.md` 与需求卡片的 AC；AC 不可测或有歧义，先退回产品澄清，不带歧义开工。
- 复述一遍「要做什么 / 不做什么 / 验收怎么算过」，确认后写进任务清单。

## 2. 技术方案（> 3 人日必写）

按 `docs/templates/tech-design.md`：目标与非目标、方案对比（至少 2 个）、数据模型与接口变更、兼容与迁移、**回滚策略**、灰度/开关、可观测性（日志/指标/告警）、性能预算、风险与依赖。方案评审通过再编码。

## 3. 编码

- 小步提交，Conventional Commits；一个提交只做一件事；AI 生成的代码在提交说明注明并自查。
- 测试先行：新逻辑必带单测，修 bug 先写复现测试；关键路径补集成测试。
- 禁止项见 `rules/dev/dev-standards.md`（`any`、裸 except、无主 TODO、密钥落地）。

## 4. 自测与 CR

- 提 CR 前：本地测试全绿 + diff 自查（正确性 / 可读性 / 测试 / AC 覆盖）+ 影响面说明。
- CR 控制在 400 行以内；评审意见 4 小时内响应；风格问题交给 lint。

## 5. 发布与守夜

- 走 `docs/templates/release-checklist.md`：变更清单、开关状态、迁移脚本、监控面板、回滚步骤、值班安排。
- 灰度先行，观察错误率 / 核心指标 / P95；异常先回滚再排查。
- 发布后 30 分钟内把观察结论写入 `current-status.md`；有事故按复盘模板留档。

## 6. 沉淀

踩坑或学到可复用经验，用 `teamai share` / `teamai contribute` 沉淀进团队知识库。
