# Demo 直达协作（demo-to-prod）

Agent 放大了每个人的开发能力，但**产出能不能进协作，取决于是否满足全队契约**。
本工作流保证：你（任何岗位）用 Coding Agent 产出的 Demo 或迭代，**不需要重构**即可
进入设计/研发/测试协作，或直接进灰度。

## 0. 先判断场景

- **A. 全新 Demo / 原型**：从零做，目标是「可演示 + 可交接」。
- **B. 已有项目迭代**：目标是「可灰度上线测试」——优先遵守项目自己的约定。

## 1. 动手前：三份契约 + 项目约定进上下文（必做）

1. 读三份全队准线：`rules/design-contract.md`（UI）、`rules/engineering-contract.md`（代码）、
   `rules/quality-contract.md`（验收与清单）。
2. 场景 B 加读：目标项目的 `AGENTS.md` / `CLAUDE.md`、目录结构、lint 与测试命令、CI 配置、
   `docs/context/current-status.md`——**项目约定优先于个人习惯**。
3. 先写 AC（质量契约第 1 条）：主流程 + 异常路径 + 数据口径。写不出 AC 先别写代码。

## 2. 开发节奏（让每一步都可运行）

- 小步提交（Conventional Commits），每步可运行可回退；核心路径先通，细节后补。
- UI 一律复用设计系统组件（设计契约第 1 条）；不发明新组件。
- 新增依赖、新增表结构、改接口 → 先停：这些会波及研发侧，写进 open-questions 请对应岗位确认。

## 3. 免重构自检（质量契约第 3 条清单，逐项跑）

| 自检 | 调用 | 通过标准 |
|---|---|---|
| UI：设计系统、状态覆盖、无障碍 | `design-reviewer` | 阻断项清零 |
| 代码：正确性、测试、AC 覆盖、可回滚 | `code-reviewer` | 阻断项清零 |
| 测试视角：核心链路三类覆盖 | `test-plan-reviewer` | 缺口已补或已标注 |
| 工程底线 | lint / 类型 / 测试命令 | 全绿（记录结果） |

Agent 的意见按「阻断/重要/建议」处理：阻断必须改，重要给结论，建议可留。

## 4. 出口二选一

**A. 交接进协作**（Demo / 原型）：按 `stage-handoff` 出交接包——
00-summary（目标/范围/AC/风险）+ 产出物（代码与演示说明）+ open-questions（需要设计/研发/
测试拍板的）+ checklist（免重构清单结果）。同步更新 `current-status.md`。

**B. 直接灰度**（已有项目迭代）：产出灰度计划——开关与放量比例（如 5% → 20% → 100%）、
观察指标与阈值、回滚步骤、值班人；发布走 `docs/lifecycle/06-release.md` 的发布检查单，
上线后守夜 30 分钟并记录结论。

## 5. 收尾（必做）

- 更新 `docs/context/current-status.md`（含自检结论与遗留项）；改了口径/方案写 `decisions.md`。
- 踩坑与可复用经验用 `teamai contribute` 沉淀。

## 边界

- 跨团队影响面大的改动（数据模型、公共接口、支付/权限）不做单人直发：先走阶段 2-4 的
  正式评审，再实现。
- 本工作流不豁免任何契约；「赶时间」不是跳过清单的理由。
