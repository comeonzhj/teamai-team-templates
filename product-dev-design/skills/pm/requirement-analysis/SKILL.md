# 需求分析与 PRD 工作流（PM）

## 1. 问题定义先于方案

问清四件事，缺一就向用户补问（一次问全，不要挤牙膏）：
- **用户**：谁遇到问题？（角色 / 场景 / 频次）
- **问题**：现在的做法是什么，卡在哪？
- **证据**：有什么数据/访谈/工单支撑？没有证据就标注「假设待验证」。
- **影响**：不做的代价是什么，做了的预期收益是什么？

产出一页纸问题定义，写进需求卡片的「问题与机会」段。

## 2. 方案与优先级

- 至少列 2 个解法（含「不做」基线），按 RICE 打分：Reach（周期内触达用户数）、Impact（3=巨大/2=高/1=中/0.5=低/0.25=微）、Confidence（100%/80%/50%）、Effort（人日）。
- 每个分数写依据；Confidence < 50% 的需求先做验证实验，不直接进排期。
- 结论写入 `docs/context/decisions.md`（谁拍的、依据、放弃了什么）。

## 3. 需求卡片与 PRD

- 单条需求用 `docs/templates/requirement-card.md`；跨团队/多迭代的需求升级为 `docs/templates/prd.md`。
- **验收标准（AC）**是核心交付：Given/When/Then 或可验证陈述，覆盖正常流、异常流、边界、数据口径、性能与兼容要求。
- 明确写「非目标（不做什么）」——它是控制范围膨胀最有效的一段。

## 4. 需求评审

- 准入：卡片完整 + 数据来源 + 研发/设计预沟通完成 + 风险初判。
- 评审目标是三方（产品/设计/研发）对**范围与 AC** 达成一致，不是讲故事。
- 评审后 24 小时内：按结论改 PRD、更新 `current-status.md`、把关键取舍记入 `decisions.md`。

## 5. 验收与闭环

上线后按成功指标出数据结论（口径 + 来源），对照需求卡片的假设，写进复盘（`docs/templates/retro.md`）。
